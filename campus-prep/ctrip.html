一、公司画像 & 校招节奏

携程集团（Trip.com Group）成立于，总部上海，纳斯达克上市（股票代码：TCOM）。核心产品涵盖携程旅行、去哪儿网、天巡（Skyscanner）、铂涛酒店集团，营收约465亿元，用户超5亿，员工约3万人。疫情后出行需求强劲复苏，携程近两年的校招规模和薪资竞争力都在明显提升。

技术特点一句话概括：Java是第一后端语言，全球化系统是最独特的技术挑战。机票预订、酒店预订、度假产品、商旅管理——这些业务涉及多语言、多时区、多货币，是国内互联网公司里罕见的全球化系统复杂度。

Java 后端开发（最大招聘方向）

携程的 Java 后端 JD 通常包含以下几个关键词，拆开来看：

1. "熟悉 Spring Cloud 生态"

不只是"会用"，是要理解原理： - Nacos 注册中心：为什么比 Eureka 更适合携程的多机房部署？ - Spring Cloud Gateway：路由配置、过滤器链怎么工作？ - OpenFeign：底层是 Ribbon 负载均衡 + HttpClient，这一点要能说清楚 - Sentinel：流控规则、熔断降级、系统保护三类策略的区别

2. "具备高并发设计经验"

携程的场景特别典型：五一黄金周订单量是平时 10 倍，机票搜索在早晚高峰时段并发极高。JD 里的"高并发"落到面试里，往往会变成： - 机票超卖问题怎么解决？（Redis 预减库存 + 数据库乐观锁） - 支付接口怎么保证幂等性？（Idempotency-Key + Redis） - 峰值流量下怎么降级？（Sentinel 限流 + 熔断）

3. "了解分布式事务"

携程业务里订单状态涉及多个服务（预订服务、支付服务、库存服务），分布式事务是真实痛点： - 本地消息表方案（机票预订常用） - Saga 模式（长事务场景） - TCC 方案的优缺点

算法工程师方向

携程算法岗侧重价格优化和推荐系统，与美团配送算法的运筹优化方向不同： - 价格优化：动态定价算法、需求预测模型（时序预测） - 推荐系统：协同过滤、召回 + 排序架构 - 搜索相关：Elasticsearch 调优、向量检索

三、LeetCode 高频题 Top 20（真实面经数据）

携程整体难度 Medium 为主，Hard 题极少出现。链表和二叉树是绝对核心，滑动窗口和动态规划是稳定第二梯队。刷透 Medium 是核心策略，不需要死磕 Hard。

第一梯队：必刷（面经中高频出现）

1. 反转链表（No.206）⭐⭐⭐⭐⭐

  • 难度：Easy
  • 核心思路：迭代三指针（prev/curr/next）+ 递归
  • 常见追问：反转链表 II（No.92，部分反转）→ K 组翻转（No.25）
  • 携程问法："给你一个机票预订链，把最近 K 个订单反转顺序展示"——本质上还是 No.25

2. 二叉树层序遍历（No.102）⭐⭐⭐⭐⭐

  • 难度：Medium
  • 核心思路：BFS + 队列，逐层收集节点
  • 常见追问：锯齿形层序遍历（No.103）、每层最大值（No.515）
  • 携程问法：直接考，或结合树形目录结构（机票分类树）

3. LRU 缓存机制（No.146）⭐⭐⭐⭐

  • 难度：Medium
  • 核心思路：HashMap + 双向链表（LinkedHashMap 偷懒版 vs 手写版）
  • 常见追问："如果是机票搜索结果的缓存，TTL 怎么设计？"——这是携程特色，要能从 No.146 联系到实际缓存系统设计
  • 注意：携程面试官会让你手写，直接用 LinkedHashMap 不够，要能解释底层

4. 无重复字符的最长子串（No.3）⭐⭐⭐⭐

  • 难度：Medium
  • 核心思路：滑动窗口 + HashMap 记录字符最新位置
  • 常见追问：最多 K 个不同字符的最长子串（No.340）

5. 合并两个有序链表（No.21）⭐⭐⭐⭐

  • 难度：Easy
  • 核心思路：递归 or 迭代，虚拟头节点技巧
  • 常见追问：合并 K 个升序链表（No.23，用堆）

刷题规律总结

1. 难度整体中等：携程笔试极少出 Hard，Medium 刷透是核心策略，不用死磕困难题

2. 链表+二叉树双高频：反转系列配合 BFS 变形，是最常见的组合拳，单独准备链表至少 3 题、二叉树至少 4 题

3. 业务场景结合：LRU 会被问"机票搜索结果的缓存怎么设计"，岛屿数量会被问"如何用图算法处理景点推荐"——看起来是算法题，实际是系统设计的开场

4. 全球化相关算法：偶有时区计算、货币转换的设计类题目，这是其他公司基本不会考的携程独家

四、技术面试考点

Java 专项（权重 ⭐⭐⭐⭐⭐）

携程后端是 Java 大厂，Java 生态的深度是每轮必考，没有例外。

JVM 考点： - GC 收集器：G1 的 Region 分区原理，为什么 G1 比 CMS 更适合携程的大堆场景 - OOM 类型和排查：堆溢出（java.lang.OutOfMemoryError: Java heap space）、元空间溢出、直接内存溢出 - 内存分析工具：jmap、jstack、MAT 分析 heap dump

并发考点： - 线程池 7 大参数（核心线程数/最大线程数/保活时间/队列/线程工厂/拒绝策略） - 4 种拒绝策略（AbortPolicy/CallerRunsPolicy/DiscardPolicy/DiscardOldestPolicy）——携程会追问"机票预订高峰期用哪种？" - AQS 原理：ReentrantLock 的公平锁/非公平锁，Semaphore，CountDownLatch 的实现

Spring 考点： - IOC：BeanFactory vs ApplicationContext，Bean 的生命周期（实例化 → 属性注入 → 初始化 → 使用 → 销毁） - AOP：CGLIB vs JDK 动态代理的选择逻辑，@Transactional 的代理实现 - @Transactional：7 种传播行为（REQUIRED/REQUIRES_NEW/NESTED 最常考），自调用失效是必考追问点

集合考点： - HashMap JDK8：数组+链表+红黑树，链表长度 ≥ 8 且数组长度 ≥ 64 时树化 - ConcurrentHashMap：JDK8 的 CAS + synchronized 分段锁，vs JDK7 的 Segment 锁

微服务架构（权重 ⭐⭐⭐⭐⭐）

这是携程的独特考点，因为携程的微服务规模非常大（数百个服务），面试官对这块要求比普通互联网公司高。

服务注册发现： - Nacos vs Eureka：Nacos 支持 AP+CP 切换，支持配置管理，比 Eureka 更全面 - Nacos 服务实例的健康检查机制（心跳 vs 主动探测）

负载均衡： - Ribbon 的三种策略：轮询（RoundRobin）、随机（Random）、权重（WeightedResponse） - 面试追问："携程有海外节点，如何实现就近路由？"——涉及 Zone 感知负载均衡

熔断限流： - Sentinel vs Hystrix：Sentinel 规则更丰富（流控/降级/系统/来源访问控制），Hystrix 线程隔离 vs Sentinel 信号量隔离 - 携程场景："机票搜索接口超时如何降级？返回缓存数据还是提示稍后重试？"

Apollo 配置中心（携程独家加分项）： - Apollo 是携程开源的配置管理系统（GitHub 上有 3 万+ Star） - 核心架构：Config Service（推送配置）+ Admin Service（管理配置）+ Portal（UI） - 长轮询机制：客户端通过长轮询感知配置变化，响应时间约 1 秒 - 面试时提到了解 Apollo，面试官会多聊几句——毕竟这是携程的骄傲

链路追踪： - Zipkin/SkyWalking：分布式链路追踪原理，TraceId 的传递机制 - 采样率设置（生产环境不能 100% 采样）

全球化系统（权重 ⭐⭐⭐⭐，携程独特考点）

这是其他互联网公司面试基本不会考的内容，但在携程是高频考点。

多时区处理： - 反面教材：直接用 new Date() 存时间，时区一变全错 - 正确做法：数据库统一存 UTC，显示时转换为本地时区 - Java 工具：ZonedDateTime（带时区的日期时间）、Instant（时间戳，无时区概念） - 常见追问："用户在北京订了一张到纽约的机票，出发时间怎么显示？"

// 正确：用 ZonedDateTime 处理
ZonedDateTime departureUtc = ZonedDateTime.of(, 3, 10, 14, 0, 0, 0, ZoneOffset.UTC);
ZonedDateTime departureCst = departureUtc.withZoneSameInstant(ZoneId.of("Asia/Shanghai"));
ZonedDateTime departureEst = departureUtc.withZoneSameInstant(ZoneId.of("America/New_York"));

多货币系统： - 汇率实时更新（外部汇率 API + Redis 缓存，TTL 5-） - 精度陷阱：货币计算绝对不能用 double，必须用 BigDecimal - BigDecimal 的 setScale(2, RoundingMode.HALF_UP) 保留两位小数四舍五入

国际化 i18n： - Spring 的 MessageSource 接口，properties 文件按语言区分（messages_zh_CN.properties / messages_en_US.properties） - 动态切换语言：LocaleContextHolder.setLocale()

全球部署： - CDN 加速（静态资源就近分发） - 跨地域容灾（主备机房 / 双活机房） - 跨地域数据同步的最终一致性问题

数据库与缓存（权重 ⭐⭐⭐⭐）

MySQL 重点： - 索引优化：机票搜索的复合索引设计（出发城市 + 到达城市 + 日期），最左前缀原则 - MVCC：快照读 vs 当前读，Read View 的生成时机 - 分库分表：携程订单表按用户 ID 分库，按时间分表，跨库查询问题

Redis 重点： - 机票价格缓存：TTL 设置多少合适？（价格频繁变化，建议短 TTL + 主动失效） - 缓存击穿：热门航线缓存过期瞬间大量请求打到数据库（互斥锁 / 永不过期策略） - 缓存雪崩：大量 Key 同时过期（随机 TTL 分散）

Elasticsearch 重点： - 机票/酒店搜索的全文检索：倒排索引原理 - 相关性评分（TF-IDF / BM25）

高并发预订场景（权重 ⭐⭐⭐⭐，携程特色）

机票超卖问题（最高频场景题）：

面试官最喜欢问："五一黄金周，某热门航班库存只剩 1 张，同时有 100 个用户在预订，如何保证不超卖？"

完整方案： 1. Redis 预减库存（DECR 原子操作，结果 < 0 则售罄） 2. 消息队列异步落库（削峰） 3. 数据库乐观锁兜底（version 字段 + WHERE version = ?） 4. 预减失败直接返回"已售罄"，无需走数据库

订单幂等性： - 支付接口防重放：客户端生成 Idempotency-Key，服务端 Redis 存储，相同 Key 直接返回历史结果 - 数据库唯一索引（订单号 + 幂等 Key 建联合唯一索引）

峰值流量处理： - Sentinel 接口限流（令牌桶 / 漏桶算法） - 热点参数限流（某个热门航班成为热点，单独限流） - 降级策略：搜索结果降级返回缓存数据，保证用户体验

五、面经规律总结

面试风格：业务理解 + Java 生态深度

收集的携程面经呈现几个清晰规律：

规律 1：业务理解是真实加分项

面试官会主动问"你了解携程的哪些业务"，能结合机票/酒店/度假业务思考技术方案的候选人，体验明显更好。比如： - 回答 Redis 缓存问题时，主动说"如果是机票价格这种频繁变化的数据，TTL 应该设短一点，同时配合价格变更时的主动失效" - 比说教科书式的"Redis 缓存有缓存穿透、缓存击穿、缓存雪崩三种问题"更有说服力

规律 2：Java 生态是核心考察，几乎每轮必问

Spring、JVM、并发三个方向，平均每轮技术面至少覆盖其中两个。没有任何一轮面试跳过了 Java 基础。

规律 3：全球化系统会被追问

多时区处理、多货币精度是高频追问点。面试官不只问"知不知道"，还会让你写代码或给出具体方案。

规律 4：Apollo 配置中心是加分项

携程内部大量使用 Apollo，面试中提到"我了解 Apollo 的长轮询机制"，面试官通常会很有兴趣深聊。

规律 5：节奏比字节友好

携程面试节奏不像字节那么紧张，给候选人思考时间，允许"我想一下"然后慢慢组织语言。整体氛围偏工程师文化，不喜欢特别强势的面试官。

高概率追问链

从面经整理出以下几条高频追问链，提前准备：

链条 1：Spring @Transactional → 追问自调用失效（A 方法调用同类 B 方法，事务不生效） → 追问为什么（AOP 基于代理，内部调用不走代理） → 追问如何解决（通过 AopContext.currentProxy() 获取代理对象，或拆到不同 Bean）

链条 2：线程池参数 → 追问 4 种拒绝策略（AbortPolicy/CallerRunsPolicy/DiscardPolicy/DiscardOldestPolicy） → 追问每种策略的适用场景 → 追问携程机票预订峰值期用哪种（CallerRunsPolicy 最常见，避免任务丢失）

链条 3：Redis 机票价格缓存 → 追问 TTL 设置多短合适 → 追问价格变化频繁时如何保证一致性（主动失效 + 短 TTL 双保险） → 追问缓存击穿如何处理（互斥锁 / 逻辑过期）

链条 4：微服务熔断 → 追问 Sentinel 的降级规则（慢调用比例/异常比例/异常数） → 追问携程业务里的降级策略 → 追问熔断后多久恢复（半开状态探测）

链条 5：多时区处理 → 追问 Java 里如何正确处理时区（ZonedDateTime vs LocalDateTime） → 追问数据库里时间字段用什么类型（DATETIME 无时区 vs TIMESTAMP 有时区限制，建议 BIGINT 存 UTC 时间戳） → 追问跨时区计算出发/到达时间差

笔试特点

  • 题型：编程题 3 道 + 选择题（Java/Spring/OS/网络，约 20-30 题）
  • 难度：Easy × 1 + Medium × 2，Hard 极少出现
  • 时间：
  • 特点：携程笔试相对友好，不会出偏僻算法题；选择题会考 Spring 注解、JVM 参数、SQL 优化这类工程向知识点
