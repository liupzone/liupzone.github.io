一、公司画像 & 校招节奏

米哈游成立于，总部上海，是国内游戏行业技术含量最高的公司之一。核心产品《原神》累计收入超50亿美元，是全球最成功的开放世界手游；《崩坏：星穹铁道》《崩坏3rd》《绝区零》构成完整的产品矩阵。营收约270亿元，员工超1万人。

如果要用一句话描述米哈游的技术特点，那就是：C++是第一语言，游戏开发经验是硬门槛，对游戏的热情是加分项。游戏引擎、客户端渲染、物理模拟，全部用C++实现。这和其他互联网大厂以Java/Go为主的技术栈有本质区别——投米哈游客户端岗，你的C++必须真的扎实，不能靠背八股文过关。

文化层面，米哈游是一家地道的"宅文化"公司。面试官大概率是二次元爱好者，对游戏开发有真实热情。这意味着面试不只是技术考察，还有一个隐性标准：你是否真的热爱游戏、热爱这个行业。真诚比套路重要得多。

核心差异点：米哈游面试与其他大厂的不同

两个考点在米哈游出现频率远高于其他公司：

头文件循环包含问题：A.h包含B.h、B.h包含A.h，这在大型游戏项目中是高频问题。其他公司几乎不考，米哈游把它当成C++工程能力的基础考核。不只是知道问题，要能说清楚3种解决方案，还要能说出前向声明的限制。

刷题规律总结

规律1：C++实现是硬要求。米哈游面试官会问"你能用C++写一遍吗？"，不接受Python提交。刷题的时候就要用C++，熟悉STL容器的用法（unordered_map、priority_queue、list），边界处理和命名规范也要注意。

规律2：计算几何题更高频。矩形面积（No.223）和直线上最多的点（No.149）在普通互联网公司出现概率很低，但在游戏公司里这类计算几何基础是实际工作会用到的，米哈游面经里出现过多次。

规律3：Hard题比普通大厂多。接雨水（No.42）、柱状图最大矩形（No.84）都在米哈游面经里出现过，说明他们对算法能力的要求在游戏行业里属于高标准。第二梯队的Hard题至少要做一遍，不能只停留在Medium。

规律4：代码质量极其重要。命名规范（驼峰/下划线要统一）、边界处理（空指针、空数组、边界条件）、注释，都在米哈游的考察范围内。游戏行业对代码工程质量要求高，这是他们的行业习惯。

四、技术面试考点

C++专项（客户端核心，权重⭐⭐⭐⭐⭐）

头文件循环包含（米哈游特色考点）

这是米哈游客户端岗的经典考题，其他公司极少考，来了必须答上。

问题场景：A.h 里 #include "B.h"，B.h 里 #include "A.h"，编译报错。

解决方案1：前向声明（Forward Declaration）

// B.h 里不用 #include "A.h"
// 只需要加一行
class A;  // 告诉编译器A是个类，但不需要知道A的完整定义

class B {
    A* a;  // 可以用指针/引用，不能实例化
};

限制：前向声明只能用指针或引用，不能调用成员函数，不能实例化。

解决方案2：Include Guard

// 在每个头文件顶部加上
#ifndef A_H
#define A_H
// 文件内容
#endif
// 或者更简单的：#pragma once

这防止同一个文件被重复包含，但不能解决真正的循环依赖。

解决方案3：重新设计依赖关系（最根本的解法）——引入第三个头文件，让A和B都依赖它，而不是互相依赖。

高概率追问："前向声明有什么限制？"——不能访问成员，不能实例化，不知道对象大小，只能用指针或引用。

GDB调试不带调试信息的程序（米哈游特色考点）

其他公司的GDB题通常假设程序是-g编译的（带符号信息）。米哈游考过一个更难的场景：线上程序是-O2优化编译的，符号表没了，怎么调试？

常用手段： - x/20i $rip：查看当前指令指针附近的20条汇编指令 - info registers：查看所有寄存器当前值 - info proc mappings：查看进程的内存映射（找到各段地址范围） - find命令：在内存区域中搜索特定值

高概率追问："程序崩溃产生了core dump文件，怎么分析？"

gdb ./program core   # 用程序+core文件启动GDB
bt                   # 查看崩溃时的调用栈

内存管理

  • RAII（资源获取即初始化）：把资源的生命周期绑定到对象，对象析构时自动释放资源，这是C++内存安全的核心思想
  • 智能指针：unique_ptr独占所有权（移动语义，零开销）；shared_ptr共享所有权（引用计数，原子操作保证线程安全）；weak_ptr打破循环引用
  • 游戏对象池：预分配一批对象，复用而不是频繁new/delete，减少内存碎片和GC压力。这是游戏开发中的常用模式，米哈游面试官可能直接问"怎么设计一个对象池"

右值引用与move语义： - std::move：把左值转换成右值引用，不做实际移动（只是类型转换），然后移动构造函数/移动赋值负责"搬家" - std::forward<T>(arg)：完美转发，保持参数原有的值类别（左值保持左值，右值保持右值）

多线程： - 游戏的多线程架构：渲染线程和逻辑线程分离，防止互相阻塞 - std::mutex/std::atomic：互斥锁和原子操作的选择场景 - 无锁队列：游戏服务器高频使用，用原子操作实现线程安全的队列

图形学专项（客户端/TA方向，权重⭐⭐⭐⭐⭐）

图形学是米哈游客户端岗和技术美术岗的核心考点，普通互联网公司基本不考这些。

渲染管线（必考）

顶点数据 → 顶点着色器（坐标变换）→ 图元装配（三角形组装）→ 光栅化（三角形变成像素片元）→ 片元着色器（计算每个像素颜色）→ 深度/模板测试 → 帧缓冲输出

这条流程要能完整说清楚，每个阶段做什么、可编程还是固定、性能瓶颈在哪。

光照模型： - Blinn-Phong：经典模型，环境光+漫反射+高光。漫反射用dot(N, L)，高光用半向量H = normalize(L+V) - PBR（物理渲染）：基于微表面理论，金属度/粗糙度工作流，原神部分场景使用

阴影技术： - Shadow Map：把光源视角渲染一张深度图，主摄像机渲染时对比深度判断是否在阴影中 - PCF（百分比近似过滤）：对Shadow Map周围多个采样点取平均，产生软边阴影效果 - 级联阴影（CSM）：不同距离使用不同分辨率的Shadow Map，解决近处锯齿/远处覆盖不足的矛盾

原神的Toon Shading（米哈游特色）： 原神的渲染风格（卡通渲染/二次元渲染）是米哈游的技术名片。核心是非真实感渲染（NPR）： - 描边效果：背面法线外扩（Outline Pass） - 色块感：对漫反射结果做阶梯化处理（step/smoothstep） - 多平台适配：PC/手机/主机性能差异巨大，需要动态调整渲染质量

性能优化： - DrawCall合批（Batching）：减少CPU向GPU提交渲染指令的次数，是移动端优化的核心 - LOD（细节层次）：远处物体用低面数模型，近处用高面数模型 - 遮挡剔除（Occlusion Culling）：不在视野内或被遮挡的物体不参与渲染

游戏服务器专项（服务端方向，权重⭐⭐⭐⭐）

游戏服务器和普通后端的差异，在于实时性和防作弊这两个独特需求。

帧同步 vs 状态同步： - 帧同步：服务端只转发操作指令，客户端各自计算，计算结果要完全一致（确定性计算）。带宽小，但对客户端一致性要求极高，任何随机数或浮点误差都会导致不同步 - 状态同步：服务端计算游戏逻辑，把结果（位置、血量等状态）发给客户端显示。结果可靠，但带宽和服务端压力更大

KCP协议（UDP可靠传输）： - TCP在弱网下延迟高（重传+拥塞控制），对实时游戏体验影响大 - KCP是基于UDP的可靠传输层，可靠性接近TCP，延迟比TCP低30%-40%，代价是更高的带宽消耗 - 面试考法："为什么游戏用UDP而不直接用TCP？"

反外挂： - 核心原则：服务端永远不相信客户端的数据，所有关键逻辑在服务端验证 - 检测思路：客户端发来的移动速度超过物理上限？伤害数值超过装备允许的上限？直接拒绝并标记

玩家数据存储： - Redis缓存热点数据（当前在线玩家的背包、属性、位置） - MySQL持久化冷数据（历史记录、交易记录） - 断线重连：玩家状态保存在服务端，重连时从Redis恢复

操作系统专项（通用，权重⭐⭐⭐⭐）

虚拟内存：游戏资源管理的核心，大型游戏资产（纹理、模型、动画）需要动态加载卸载，虚拟内存管理直接影响游戏内存占用

IO模型：epoll在游戏服务器中的应用——游戏服务器需要同时处理大量连接，epoll的事件驱动模型比select/poll效率高

多线程渲染架构： - 渲染线程和逻辑线程分离：逻辑线程计算游戏状态，渲染线程负责提交GPU命令，双缓冲避免互相等待 - 工作线程池：物理计算、AI寻路、资产加载，这些耗时操作放到工作线程异步处理

AI工具提升生产力（米哈游特色考察）： 米哈游内部鼓励使用AI辅助开发，面试可能问： - 你用过哪些AI工具提高开发效率？（Claude Code、Copilot等） - 如何用AI辅助Shader代码开发？ - AI生成内容在游戏中的应用（NPC对话、程序化地形、动画生成）

这个考点在其他公司几乎不会出现。如果你有相关实践，主动提出来是加分项。

五、面经规律总结

面试风格画像

米哈游面试有一个其他大厂没有的特点：面试官会把技术问题和游戏实际场景结合起来。问你渲染管线，可能紧接着问"原神的Toon Shading是怎么实现的"；问你内存管理，可能接着问"游戏对象池的设计思路是什么"。面试官本人就是游戏开发者，他们问的问题是他们在工作中真正遇到的。

面试氛围偏技术讨论而非答题式审问，但追问会深到你答不上来为止。C++岗的面试轮数也更多——2-4轮技术面很常见，每轮关注的方向不完全相同，前几轮基础扎实，后几轮考设计能力和项目经验。

必须展示游戏热情。面试官几乎一定会问"你玩过原神吗？"或者"你对哪个技术方向最感兴趣？"。不需要伪装成狂热粉丝，但如果你完全不了解游戏行业、对游戏开发没有任何兴趣，很难通过。真诚地说出你对游戏技术的哪个方向感兴趣（渲染/服务器/工具链/物理引擎），比背诵套话有用得多。

高概率追问链

头文件循环包含追问链：

头文件循环包含怎么解决？
→ 追问：前向声明有什么限制？（不能访问成员，不能实例化，只能用指针/引用）
→ 追问：include guard 和 #pragma once 的区别？
  （include guard 是标准C++，#pragma once 是编译器扩展，但几乎所有主流编译器都支持）
→ 追问：如果两个类需要互相包含完整类型（不能用指针），怎么办？
  （重新设计依赖关系，引入第三个基类或接口）

GDB调试追问链：

不带调试信息的程序怎么调试？
→ 追问：core dump 文件怎么生成？（ulimit -c unlimited，程序崩溃后自动生成）

→ 追问：有没有用过其他性能分析工具？（VTune、perf、Valgrind）

描述一下渲染管线的流程

  （描边用背面法线外扩，卡通感用阶梯化漫反射）
→ 追问：移动端如何优化 DrawCall？
  （静态合批/动态合批/GPU Instancing，减少状态切换）
→ 追问：Shadow Map 有什么问题？怎么改进？
  （阴影锯齿、自阴影，PCF/PCSS软阴影，CSM级联）

内存管理追问链：

游戏对象池的设计思路？

校招节奏

整体策略

米哈游备考有一个核心原则：C++深度和图形学基础必须提前投入，不能临时抱佛脚。这两个方向的知识点不是背几条八股文就能应付的，面试官自己就是游戏开发者，问的问题来自真实工作场景，背出来的答案他们一听就知道。

如果只有，优先级排序：C++专项（头文件/GDB/内存管理）> 渲染管线/图形学基础 > 游戏开发特色知识（KCP/帧同步/对象池）> 算法题（Hard题/图形学算法） > 操作系统网络。服务端方向的同学可以跳过大部分图形学，把这部分时间放到游戏服务器架构上。

详细计划

阶段 时间 重点任务 每日用时
Phase 1：C++深度 头文件循环包含3种解法（前向声明/include guard/重新设计依赖）；GDB调试不带符号信息；智能指针原理（shared_ptr控制块+引用计数）；右值引用和move语义；多线程（mutex/atomic）
Phase 2：图形学基础 渲染管线完整流程（每个阶段的输入输出）；Blinn-Phong光照模型手算；Shadow Map原理+PCF+CSM；原神Toon Shading实现思路；DrawCall合批/LOD/遮挡剔除
Phase 3：游戏开发特色 帧同步vs状态同步（各自适用场景、优缺点）；KCP协议（为什么比TCP延迟低）；游戏对象池设计（预分配/循环利用/模板实现）；反外挂原理（服务端验证）
Phase 4：操作系统+网络 多线程渲染架构（渲染线程+逻辑线程分离）；epoll在游戏服务器的应用；虚拟内存和游戏资产管理；SIMD指令和内存对齐
Phase 5：算法专项 Hard题（接雨水No.42/柱状图最大矩形No.84）；计算几何（矩形面积No.223/直线上最多的点No.149）；链表全系列（用C++实现）；LRU手写（C++，哈希表+双向链表）；快速排序手写 2-
Phase 6：冲刺 玩原神，了解游戏体验/技术亮点；看最新米哈游面经；整理项目中C++和图形学相关的亮点；AI工具使用经验整理；模拟面试
